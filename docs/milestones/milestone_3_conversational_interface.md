# Milestone 3 — Deterministic Conversational Interface for Business Users (DRAFT v2)

We are building V0.1 of a conversational BI application for structured financial data.

## Current environment

- Source CSVs are in Amazon S3 and exposed through Athena typed views (Task 1).
- A governed semantic layer and a deterministic query service exist in `bi_service/` (Milestone 2):
  `QuerySpec` → validate → compile → Athena → `QueryResult`. It has no raw-SQL input path.
- The approved metrics, dimensions and golden examples are in `semantic/*.yaml`.
- The read-only runtime IAM user is `analytics-query-runtime`, using workgroup `analytics_poc_wg` (1 GB scan cap).
- Development is on Windows through Claude Code. The region is ap-south-1.

Do not recreate existing AWS infrastructure, and do not change how `bi_service` compiles SQL.

## Objective

Give business users a chat-style interface where they type questions in business language and get
governed answers (a short answer sentence, a table, a chart, and how it was calculated) with **no LLM in the loop**.

Questions are interpreted **deterministically** from a governed business catalog (KPI definitions, synonyms,
dimension values, period phrases) and from approved example questions. The same question always produces
the same `QuerySpec`, the same SQL and the same answer.

**Do not invoke Amazon Bedrock or any other LLM** (at runtime, in tests, or for answer text).

## Principles

- **Deterministic end to end.** Interpretation is rule- and dictionary-based; answers are rendered from templates.
- **Governed vocabulary.** Every word the system understands comes from an approved catalog entry. Nothing is inferred.
- **Show the interpretation.** Before or with every answer, show what was understood as editable chips
  (metric, breakdown, filters, period). The user can correct any chip with a dropdown, so a misread never needs retyping.
- **Ask, don't guess.** If the metric is missing or ambiguous, or a word is unrecognised, ask with clickable options.
- **Refuse clearly.** Questions outside the catalog (customer lookups, unapproved KPIs, forecasts) get a fixed refusal
  with the closest supported questions.

## Phase A — Business catalog (definitions, synonyms, KPIs)

This is the core of the milestone. Today the KPI definitions live in `semantic/metrics.yaml`, and there is no synonym or
glossary layer. Add a governed catalog that both the interpreter and the UI read from.

### A1. `semantic/glossary.yaml`: KPIs and business terms

For each approved metric (linked by `metric_id`, so definitions are never duplicated):
- business name, short definition, long definition (plain language)
- formula in business terms (e.g. "NPA outstanding ÷ total outstanding")
- **synonyms** (e.g. gross_npa_ratio: "GNPA", "gross NPA", "NPA %", "NPA ratio")
- unit and display format (₹ Cr / ₹ L / % / count)
- behavior note for users ("month-end balance; cannot be added across months")
- owner and approval status (`approved` / `pending_approval`); only approved entries are used
- related KPIs and example questions

For each dimension: label, synonyms (e.g. state_name: "state", "region", "geography";
branch_code: "branch", "office"), and description.

Business terms that are **not** metrics (e.g. "PAR", "DPD", "Ticket size", "Fiscal year") get glossary entries for the
catalog page only.

### A2. `semantic/value_aliases.yaml`: dimension values

- Value dictionaries for low-cardinality, non-PII dimensions (state, loan group, product, branch, PAR bucket, ticket size,
  account status, business nature, flags). These are generated by an **aggregate-only** `SELECT DISTINCT` refresh script,
  reviewed, then committed.
- Aliases, e.g. "TN" → Tamil Nadu, "MH" → Maharashtra, "90+" → "90+ DPD", "NPA accounts" → npa_flag = true,
  "current" → par_bucket = Current.
- Never identifiers or PII.

### A3. `semantic/period_phrases.yaml`: time language

Deterministic patterns, all resolved against the latest available snapshot date (not today's date):
- "latest", "current", "as of now", "this month"
- "March 2026", "Mar-26", "2026-03"
- "FY26", "FY 2026", "FY 2025-26", "this/last fiscal year"
- "Q4 FY26", "last quarter", "last 3/6/12 months", "YTD", "FYTD"
- "between Jan 2026 and Mar 2026"
- "monthly", "quarterly", "yearly", "trend": time-grain words that become a time dimension

### A4. Catalog governance

- Loader cross-checks: every synonym maps to exactly one approved metric/dimension/value, with no collisions across
  entries. Every `metric_id` exists in `metrics.yaml`. Every value exists in the refreshed value dictionary.
- Changes go through review (`pending_approval` → `approved` by the business owner).
- A generated **catalog document** (`docs/catalog.md`) and the in-app **Catalog page** are rendered from the same YAML.

## Phase B — Query service enhancements (small, deterministic)

From the Milestone 2 chat test:
- `QuerySpec.include_total`: an overall row computed correctly (Σnum/Σden for ratios, the same snapshot date for balances).
- Display formatting driven by glossary units (₹ Cr, %, counts). Raw values stay in the result.
- Period labels: "Mar 2026", "Q4 FY26", "FY 2026" (convention needs approval).
- `QueryResult.snapshot_date`: the actual month-end used for snapshot metrics.
- A top-N option: sort by value plus a limit ("top 5 branches by outstanding").

## Phase C — Deterministic interpreter (`bi_chat/`, depends on `bi_service`)

Pipeline: question → normalise → match → build `QuerySpec` → validate → (answer | clarify | refuse).

- `normalizer.py`: lowercase, strip punctuation, expand known abbreviations, tokenise.
- `matcher.py`: longest-phrase dictionary matching against the catalog:
  - metric synonyms → `metric`
  - "by / per / across / split by <dimension synonym>" → `dimensions`
  - value aliases → `filters` ("in Tamil Nadu", "for Growth Finance", "excluding Delhi" → `not_in`)
  - period phrases → `period` and/or a time dimension
  - "top N / bottom N / highest / lowest" → `sort` + `limit`
- `example_matcher.py`: if direct matching is incomplete, rank `examples.yaml` questions (plus approved paraphrases)
  by token overlap and offer the top 3 as "Did you mean…" buttons. **Never execute a fuzzy match without the user clicking it.**
- `interpreter.py`: returns one of:
  - `Interpreted(spec, understood_terms, unrecognised_terms=[])`, which executes
  - `Clarify(reason, options[])`, e.g. a missing metric, two metrics matched, or an unrecognised word
  - `Refuse(reason, suggestions[])`, e.g. a customer/account lookup, an unapproved KPI, or a forecast
  Rule: execute only when exactly one metric matched and **every** meaningful token was recognised (after stop-words).
- `conversation.py`: deterministic follow-ups that modify the previous spec, e.g.
  "now by branch", "same for FY25", "only Tamil Nadu", "remove the filter", "show as a trend".
- `answer_renderer.py`: template sentences per metric behavior, e.g.
  "Gross NPA ratio was **2.62%** at 31 Mar 2026 (₹53.34 Cr of ₹2,034.10 Cr). Highest: Tamil Nadu 7.87%."
  Every number is taken from the `QueryResult`.

## Phase D — Streamlit interface

- **Chat page.** Message history; answer sentence; formatted table; automatic chart (line for time, bar for categories,
  KPI card for a single value). Interpretation chips (metric / breakdown / filters / period) with dropdown editing.
  Clarification and "Did you mean" options as buttons. A "How this was calculated" expander showing the definition,
  formula, period, snapshot date, query id and bytes scanned. Generated SQL is shown to admins only.
- **Catalog page.** Searchable KPI list with definitions, formulas, synonyms, units, behavior notes and example questions,
  plus dimensions and their values. Clicking an example runs it.
- **Guided builder** (fallback). Pick a metric, breakdown, filters and period from dropdowns. It produces the same `QuerySpec`.
- CSV download of aggregate results, and 👍/👎 feedback with a comment (stored locally for catalog tuning).

## Phase E — Security and operations

- The runtime identity stays `analytics-query-runtime` (Athena read-only). No Bedrock permissions.
- V0.1 hosting: local Streamlit only (shared hosting and authentication are a later decision).
- Audit log per question: timestamp, question text, interpretation outcome, `QuerySpec`, status, query_id, latency,
  bytes scanned. No result rows. Unrecognised terms are logged so they can be added to the catalog.
- A rate limit per session, and the existing 1 GB scan cap and 60 s timeout.
- Refuse any question that mentions an identifier pattern (account number, customer id, PAN, phone).

## Phase F — Evaluation and testing

- **Interpretation test set** (`tests/eval/questions.yaml`, ≥ 60 questions): question → expected `QuerySpec`, or expected
  clarification/refusal. Coverage:
  - every approved metric and synonym
  - every dimension
  - value aliases
  - all period phrases
  - top-N
  - follow-ups
  - ambiguous questions, misspellings, out-of-scope questions, and PII/account lookups
- Unit tests: normaliser, matcher (longest match, collisions), period parsing (fiscal-year edges, "last quarter" relative
  to the latest snapshot), conversation follow-ups, answer templates (numbers equal the result), catalog cross-validation.
- UI smoke test with a mocked `QueryService`.
- Live run of the golden questions in paraphrased form, only with approval.

## Acceptance criteria

1. All 7 golden questions, asked in at least 3 phrasings each, produce the same `QuerySpec` and results as Milestone 2.
2. 100% of the interpretation test set passes. Interpretation is deterministic, with an identical spec on repeated runs.
3. Unrecognised or ambiguous questions always produce a clarification or "Did you mean", never a silent guess.
4. 100% of customer/account-level and out-of-scope questions are refused.
5. Every KPI shown in the UI has a catalog entry with definition, formula, synonyms and unit, sourced from YAML.
6. No LLM or Bedrock dependency anywhere (enforced by test). No row-level or PII data in logs.
7. Median response time ≤ 5 s for a single query.
8. All tests pass locally. `bi_service` is unchanged except for the Phase B enhancements.

## Known limitation (accepted for V0.1)

A dictionary interpreter only understands the vocabulary in the catalog. Coverage grows by adding approved synonyms
from the unrecognised-terms log, not by guessing. Free-form or multi-part questions ("compare NPA and PAR by state and
explain why") are out of scope. They are answered with a clarification or the guided builder.

## Forward compatibility (Milestone 4: Bedrock)

Bedrock is planned as the next milestone. Design for it now without invoking it:
- **Swappable interpreter.** Define an `Interpreter` protocol returning `Interpreted | Clarify | Refuse`. The deterministic
  interpreter is the only V0.1 implementation; an LLM interpreter can be added later behind the same interface.
- **Catalog as context.** The glossary, value aliases and period phrases are the context an LLM interpreter would receive.
- **Shared benchmark.** The interpretation test set is the benchmark for any future interpreter.

## Out of scope for V0.1

LLMs (including Bedrock), joins across views, new metrics without approval, row-level drill-down, forecasting,
scheduled reports, shared hosting and authentication.
